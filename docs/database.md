# BebshaOS Database Architecture

This document describes the design principles and architecture of the BebshaOS backend database, built on PostgreSQL and Prisma ORM.

## 1. Entity Overview

The core domains of BebshaOS are:
- **Identity & Access**: `User`, `Session`, `Otp`, `Role`, `Permission`, `RolePermission`.
- **Multi-Tenancy**: `Organization`, `Branch`, `OrganizationMember`.
- **Business Entities**: `Customer`, `Supplier`, `Category`, `Product`.
- **Inventory Management**: `Inventory`, `InventoryMovement`.
- **Financial Transactions**: `Sale`, `SaleItem`, `Purchase`, `PurchaseItem`, `Payment`, `Expense`.
- **Accounting**: `LedgerEntry`, `Invoice`.
- **Subscriptions**: `Plan`, `Subscription`.
- **System**: `Notification`, `AuditLog`.

## 2. Relationship Overview

All major entities are rigidly bound to an `Organization` for strict multi-tenancy.
- Relationships between core entities and financial tables (e.g., `Product` to `SaleItem`, `Customer` to `Sale`) use **Restrict** constraints. This ensures that accidental deletion of a product or customer does not cascade and destroy historical financial data.
- Relationships linking items to an Organization use **Cascade** constraints, so deleting a tenant cleans up their data.

## 3. Multi-Tenant Strategy

- Every operational table (Customer, Sale, Product, etc.) includes an `organizationId` foreign key.
- `organizationId` must be explicitly verified and appended at the service logic layer on every read, write, and update operation to prevent tenant data leakage.

## 4. Financial Data Strategy

- All monetary values (`amount`, `total`, `discount`, `tax`, `price`) are stored as **Decimal** with a precision of `(19, 4)` in PostgreSQL. Float is strictly avoided to prevent precision loss.
- Static fields like `currentDue` on a Customer or Supplier are avoided; instead, the `LedgerEntry` table acts as the source of truth for all balances.

## 5. Ledger Strategy

The `LedgerEntry` is the immutable accounting log for BebshaOS.
- **Immutability**: A LedgerEntry should never be modified or physically deleted.
- **Reversals**: If a financial mistake occurs, a compensating entry (e.g., an `ADJUSTMENT` or `REFUND`) is posted to balance the ledger.
- **Representation**: An entry has an absolute `amount` (Decimal) and a `side` (Enum: `DEBIT` or `CREDIT`).

## 6. Inventory Strategy

- **Inventory**: Represents the current snapshot of product quantity per branch.
- **InventoryMovement**: An immutable log of every stock change (`STOCK_IN`, `SALE`, `TRANSFER`, etc.). It records the `beforeQuantity` and `afterQuantity` to trace any discrepancies.

## 7. Subscription Strategy

The `Plan` model dictates the limits of an organization's subscription (e.g., `maxBranches`, `maxProducts`). This is decoupled from the hardcoded business logic, allowing new pricing tiers to be defined via the database without code changes.

## 8. Indexing Strategy

- **Foreign Keys**: Indexes are placed on frequent relation lookups like `customerId`, `supplierId`, and `productId`.
- **Uniqueness**: Composite unique indexes are used for scoped data, e.g., `(organizationId, sku)` for Products and `(organizationId, code)` for Branches.
- **Dates**: Indexes are present on `createdAt` and `transactionDate` fields to speed up reporting and time-series queries.

## 9. Soft-Delete Strategy

- Soft deletes (`deletedAt`) are used only on business operational tables like `Customer`, `Supplier`, and `Product`. This allows hiding them from active queries while preserving the foreign-key links to historical `Sale` or `Purchase` records.
- Financial transactions (`Sale`, `LedgerEntry`, etc.) do not use soft deletes. They must either be formally cancelled via status updates or reversed via ledger adjustments.

## 10. Offline Synchronization Considerations

To support the future Android Kotlin client with offline-first capabilities (Room + WorkManager), critical tables feature synchronization metadata:
- `clientId`: A string (typically UUID) generated by the mobile app before syncing. Used as an idempotency key to prevent duplicate inserts if a network request drops the response but succeeds on the server.
- `serverCreatedAt`: The timestamp when the server acknowledged the record, which may differ from when the client initially captured it locally.
- Supported on: `Customer`, `Product`, `Sale`, `SaleItem`, `Payment`.
